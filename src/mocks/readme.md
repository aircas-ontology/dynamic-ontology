# Mocks 目录规范

## 1. 目录职责与边界

`src/mocks` 存放开发、演示和测试使用的业务样例数据，不作为正式数据源。

- 【必须】Mock 按页面或业务域分类，并与正式接口契约保持一致。
- 【禁止】正式业务代码直接依赖仅在 Mock 中存在的结构或字段。
- 【禁止】包含真实账号、令牌、个人信息或生产数据。

## 2. 结构与命名

```text
src/mocks/
└─ <domain>Mock/
   └─ <domain>Mock.ts
```

- 【必须】目录和文件使用小驼峰，文件以 `Mock.ts` 结尾。
- 【必须】一个 Mock 模块只承载一个页面或业务域。
- 【优先】大型场景按语义拆分文件，禁止用 `data1`、`test2` 等名称区分。

## 3. 类型与依赖

- 【必须】直接复用 `@/types` 导出的正式业务类型，不重复声明近似类型。
- 【必须】API Mock 使用与正式请求一致的 `ApiResponse<T>` 结构。
- 【禁止】Mock 类型通过 `any`、类型断言或关闭检查绕过正式契约。
- 【优先】Mock 数据使用具名导出，便于按场景引用。

## 4. 数据与场景

- 【必须】数据确定、可重复，默认不依赖当前时间、随机数或外部网络。
- 【必须】按需要覆盖成功、空数据、失败、权限不足和边界值场景。
- 【必须】分页、枚举、可空字段和标识符符合正式接口语义。
- 【禁止】在 Mock 文件中操作组件状态、Store、DOM 或路由。

## 5. 错误与异步行为

- 【必须】模拟错误时保留与正式请求层一致的错误结构和状态语义。
- 【优先】延迟、超时等行为由统一 Mock 适配层控制，不散布在数据定义中。
- 【禁止】通过永久 Promise 或不可控定时器制造加载状态。

## 6. 变更检查清单

1. 是否归入正确页面或业务域并符合命名规则。
2. 是否复用正式类型和响应结构。
3. 是否覆盖本功能需要的正常、空和异常场景。
4. 是否不存在真实敏感信息、随机不稳定数据和业务副作用。
5. 正式类型变更后是否同步校验 Mock。
