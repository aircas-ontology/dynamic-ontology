# Stores 目录规范

## 1. 目录职责与边界

`src/stores` 使用 Pinia 管理需要跨组件共享、跨页面协作或持续存在的业务状态。

- 【必须】局部 UI 状态保留在组件内，不因方便而提升到 Store。
- 【禁止】Store 直接操作 DOM、创建视图节点或依赖组件实例。
- 【禁止】把可由现有状态计算得到的数据重复保存为另一份可变状态。

## 2. 文件与标识命名

- 【必须】文件和导出的 Store 使用 `use<Domain>Store.ts`、`use<Domain>Store` 格式。
- 【必须】Pinia Store ID 使用唯一、稳定的 camelCase 领域名称。
- 【优先】一个文件维护一个高内聚业务域，避免全局万能 Store。

## 3. 类型、状态与更新

- 【必须】State、Getter 和 Action 保持完整类型推断，不使用 `any` 绕过检查。
- 【必须】通过 Action 表达有业务含义的状态变化，调用方不得复制更新规则。
- 【优先】对象和集合更新创建新值，避免外部持有可变引用。
- 【必须】第三方 Map、Viewer、Chart 等复杂实例不使用 `reactive()` 深度代理；确需共享时使用 `shallowRef()` 或 `markRaw()` 并明确所有权。

## 4. 异步行为与错误

- 【必须】异步 Action 按根规范区分查询、命令和初始化状态，并阻止相同请求无控制重复触发。
- 【必须】异常向调用方返回或抛出明确结果，不静默吞掉。
- 【优先】页面卸载后取消不再需要的请求，并避免过期响应覆盖新状态。
- 【禁止】在 Store 中持久化密码、令牌明文或不必要的敏感数据。

## 5. 生命周期与重置

- 【必须】持有订阅、监听器、定时器或第三方实例的 Store 提供明确初始化和销毁方法。
- 【必须】用户退出、领域切换或功能卸载时可将状态恢复到确定初值。
- 【禁止】模块导入时隐式启动长期任务。

## 6. 变更检查清单

1. 状态是否确需共享，Store ID 和文件名是否符合规范。
2. 更新规则是否集中在 Action，派生数据是否使用 Getter。
3. 异步状态、错误、并发和过期响应是否处理。
4. 复杂实例是否避免深度响应式且能完整释放。
5. 是否具有状态初值、Action 和重置行为的单元测试。
